## Implementation details

- Signup calls `auth.signUpWith(Email)` with the exact redirect and a display-only
  name. Successful confirmation-required responses show check-inbox messaging;
  they do not fabricate an authenticated user or claim email delivery.
- Login calls `auth.signInWith(Email)`. Before exposing a verified session, the
  app retrieves the current user from Supabase and checks email confirmation.
- Logout uses `auth.signOut(SignOutScope.LOCAL)`. Successful logout clears SDK
  session/verifier storage, recovery context and account navigation history. A
  failed network logout shows an error and does not falsely report sign-out.
- Native cold-start and `onNewIntent` handling feed PKCE callbacks to the same
  ViewModel. Callbacks arriving during startup restoration wait for it rather
  than being dropped. Intent data is cleared after consumption.
- Only exact callback URIs with a single code or provider error are accepted.
  URL-supplied access/refresh tokens, duplicate parameters, fragments and
  arbitrary `type=recovery` flags are rejected. No implicit token import occurs.
- Signup and recovery bind an encrypted local flow kind and creation time to the
  saved PKCE verifier. Only a successful Supabase code exchange can establish a
  recovery context. The flow expires locally after one hour; the server can
  expire/reject it earlier. Used codes cannot be reused after verifier deletion.
- Recovery emails use `auth.resetPasswordForEmail`. The generic accepted-request
  text does not disclose whether an account exists. Reset requires a verified
  recovery context on this device, expires locally after 30 minutes, and calls
  `auth.updateUser` with the new password. After success the context is removed
  and the user remains signed in; the UI reports that behavior.
- SDK 3.2.3's resend method omits both PKCE challenge and redirect. Verification
  resend uses the SDK's existing HTTP transport, public-key handling and auth
  error parser against the standard `/auth/v1/resend` endpoint, with S256 and
  `redirect_to`. No SDK/dependency upgrade was made.
- Sessions and verifier/recovery data use the existing Keystore/AES-GCM atomic
  ciphertext storage under noBackupFilesDir. Passwords are never saved. Raw SDK
  sessions/tokens/links never enter Compose saved state or diagnostic messages.
- Restoration explicitly loads SDK storage, refreshes expired tokens when
  possible and validates the user online. Loading is bounded by a timeout.
  Unavailable/expired sessions route to login/retry; there is no offline grant of
  access based solely on a cached user object. SDK auto-refresh changes are
  observed, including network and server failure states.
- The ViewModel owns coroutines and immutable state. It prevents duplicate
  submissions and handles cancellation. Password inputs are cleared on submit.
  All 23 `auth_*` message keys exist in both English and Filipino resources.
- Authenticated users reach the existing business-onboarding preview and Profile.
  Creating businesses remains explicitly unavailable until M2.3. Demo is a
  separately labeled mode backed only by DemoStore; auth does not mutate or sync
  its businesses, transactions, stock, cart, roles or entitlements.

## Known limitations and security boundaries

- End-to-end registration, confirmation, login, recovery, SDK/Keystore session
  persistence, restoration and logout require the device tests above. They are
  not reported as working live based on compilation or fake-repository tests.
- PKCE confirmation/recovery must be completed on the device that requested it,
  using the latest link. Only one pending link flow is retained per app/project.
  Uninstalling or clearing storage loses the verifier; request a fresh link.
- The custom scheme is appropriate for development. A verified HTTPS Android App
  Link remains production hardening work. Server code exchange and saved PKCE
  verification protect against granting a session from arbitrary intent data.
- Logout revokes the current refresh session. Already issued JWT access tokens
  can remain valid until expiry; no business-data authorization is implemented
  here. Do not treat client navigation as future backend authorization.
- Storage/key invalidation fails closed. Persistent Keystore failures may require
  clearing this device's app data; Android-specific failure and backup/transfer
  behavior still needs physical-device validation.
- Email SMTP restrictions, rate limits, security scanners and redirect/template
  settings can prevent delivery or consume/expire a link. Errors are surfaced;
  acceptance messaging is conditional rather than a claim of delivery.
- The signup display name is user-editable metadata and is never used for roles
  or authorization. No M2.3 tables, memberships, employee permissions, billing or
  business sync were added. Business creation is still an explicit preview.
- Language choice remains session-only pending M2.4. Play App Bundle language
  delivery and production signing remain later release work.
