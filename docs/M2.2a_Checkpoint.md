## Configuration and prerequisites for M2.2b

1. Create/select a dedicated TindaFlow project in the Supabase dashboard.
2. Enable email/password and keep email confirmations ON.
3. Register the exact allowed development redirect **`tindaflow://auth/callback`**.
   Configure verification and recovery email templates for the selected PKCE flow.
   Confirm email delivery availability/SMTP restrictions and quotas using a
   dedicated test email account.
4. Locally copy the template, without overwriting an existing configuration:

   ```powershell
   Copy-Item .\supabase.properties.example .\supabase.local.properties
   ```

5. Edit that ignored file locally with only `SUPABASE_URL` (HTTPS project origin)
   and `SUPABASE_PUBLISHABLE_KEY` (publishable key). Do not paste credentials in
   chat or screenshots. Do not add server keys, JWT keys, database credentials,
   passwords or session tokens. Gradle rejects unexpected fields and nonpublishable
   keys without printing their contents. An empty configuration remains buildable.
6. Approve M2.2b before wiring the real account journeys and callback handling.

The callback URL is reserved in code, **not registered in the Android manifest
or handled yet**. No incoming URI can create a recovery context in M2.2a. URL
shape checking alone is explicitly not evidence of verification. M2.2b must
validate callback parameters, exchange codes with the originating PKCE verifier,
handle errors/expiry/replay, and bind a real recovery session before resetting a
password. A verified Android App Link should replace the custom scheme for
production to reduce link interception risk.

## Behavior and security limits

Approved screens still validate form inputs and call an availability check only.
No passwords are passed to the repository by these screens. ViewModel entry
points for later journeys are compiled and tested with a fake repository, but
they are not wired to form submissions. The real repository cannot authenticate,
restore, send email, reset a password or sign out a real session in this milestone.
It never initializes the SDK client. Business previews remain nonfunctional and
sample workspaces remain isolated in explicit demo mode.

The client factory overrides the SDK's default storage using its supported
SessionManager/CodeVerifierCache interfaces. AES-GCM ciphertext is stored in
noBackupFilesDir, with a project-scoped Keystore key and authenticated purpose
binding. There is no plaintext SharedPreferences or plaintext fallback. SDK
logging is disabled. Encryption failures propagate instead of fabricating a
session. Unit tests cover the cryptographic envelope, **not Android Keystore or
actual SDK persistence on a phone**. Those need device validation in M2.2b/c,
including process death, failed token refresh, corruption and key invalidation.

New navigation gate functions are contracts for later live routes; they do not
replace the approved M2.1 preview routes. Current root session behavior stays
signed-out/demo-only. No live workspace membership, roles, schema, billing,
inventory/sales sync, analytics or social login was added.

## Phone regression checklist for this foundation

With a physical device connected and USB debugging enabled:

```powershell
& "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe" -d install -r .\app\build\outputs\apk\debug\app-debug.apk
```

1. Confirm Welcome and all approved account screens retain their design. Valid
   form submissions without local configuration must show an honest missing-setup
   message and stay signed out. No email or completed auth action may be claimed.
2. Verify English/Filipino notices, keyboard handling, password visibility,
   field validation, Back navigation, rotation, large fonts and TalkBack.
3. Explore demo: verify Dashboard, Sales, New Sale, Inventory and Orders, including
   checkout, stock updates, profile return, workspace switching and cleared carts.
4. Repeat availability checks in airplane mode. They must remain missing setup,
   not claim either successful authentication or an attempted network operation.
5. If configuration is filled locally and the APK rebuilt, valid account actions
   must show that live authentication is not enabled in this build. This is
   deliberate M2.2a behavior, not evidence that the project/key is valid remotely.

Actual registration, confirmation email, password recovery, login, session
restoration, sign-out and offline/provider error acceptance tests wait for
M2.2b implementation and M2.2c device verification.
